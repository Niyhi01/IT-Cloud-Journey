PHASE 2 OVERVIEW
Why a domain changes everything
Every machine in Phase 1 was standalone — local accounts, local policies, nothing shared. A domain is what turns 50 separate computers into one manageable environment: one place to create a user, one place to push a password policy, one place to see who has access to what. This month builds that environment from a blank VM, manages it for real, and automates the repetitive parts.

Phase 2 is 30 days across 4 weeks. Week 5 stands up your first Windows Server domain controller, in the correct order (static IP, DNS, then AD DS, then DHCP). Week 7 mirrors that work on the Linux side: a Samba file server, SSH hardening, cron automation, and log analysis. Week 8 closes with real automation — a PowerShell script that bulk-provisions users from a CSV — plus backup discipline and the capstone: a fully documented small-business IT environment.

D32
Static IP + DNS Server role — in that exact order
Why a domain controller can never run on a DHCP-assigned address
Build▼
Why this step comes first, non-negotiably

Active Directory depends on DNS to function — clients find domain controllers through DNS SRV records, not by IP. If the server's IP can change (as it would on DHCP), every client's cached DNS records for that domain controller become stale, and authentication starts failing in ways that look unrelated to DNS at all. Set a static IP first, every time.

1
Set a static IP on the server VM through Network Settings — pick an address in your lab's private range, e.g. 192.168.56.10.
2
Open Server Manager → Add Roles and Features → select DNS Server. Complete the installation before touching AD DS.
3
Verify: Get-Service DNS in PowerShell should show it running. nslookup localhost should resolve against your own server.

Build▼
The promotion itself
1
Server Manager → Add Roles and Features → Active Directory Domain Services. Install the role, then use the "promote this server to a domain controller" prompt that appears.
2
Choose "Add a new forest" and name your domain — something like corp.lab works well and won't conflict with any real domain.
3

Get-ADDomain Get-ADForest dcdiag /v # comprehensive domain controller health check — read the output, don't just glance at it
COMMON MISTAKE Skipping dcdiag because the GUI "looks fine." dcdiag catches DNS registration issues, replication problems, and service failures that the GUI won't surface clearly. Run it after every domain controller change you ever make, in this lab or a real one.

D38
Organizational Units — modeling a real company structure
Sales, IT, and Management OUs — the container Group Policy and delegation will target
Foundation▼
What an OU actually is

An OU is a container used to organize users, groups, and computers so Group Policy and delegated permissions can target the right subset of the domain. Without OUs, every policy applies domain-wide or not at all — no way to give Sales a different desktop restriction than IT.

create the OU structure via PowerShell
New-ADOrganizationalUnit -Name "Sales" -Path "DC=corp,DC=lab" New-ADOrganizationalUnit -Name "IT" -Path "DC=corp,DC=lab" New-ADOrganizationalUnit -Name "Management" -Path "DC=corp,DC=lab" # Verify Get-ADOrganizationalUnit -Filter *
D39
Users and security groups — the access model
Creating individual users, then grouping them for scalable permission management
Build▼
Why groups, not individual permissions

Granting permissions to individual users doesn't scale — when someone joins Sales, you'd have to remember every resource they need access to and grant each one manually. Granting permissions to a Sales security group, then adding the user to that group, means access is correct automatically the moment they're added.

create a few real users and a security group
New-ADUser -Name "Amaka Johnson" -SamAccountName "ajohnson" \ -Path "OU=Sales,DC=corp,DC=lab" \ -AccountPassword (ConvertTo-SecureString "P@ssw0rd2026!" -AsPlainText -Force) \ -Enabled $true New-ADGroup -Name "Sales-Team" -GroupScope Global -Path "OU=Sales,DC=corp,DC=lab" Add-ADGroupMember -Identity "Sales-Team" -Members ajohnson # Verify membership Get-ADGroupMember -Identity "Sales-Team"
D40–41
Group Policy Objects — 3 real policies, built and tested
Password policy, drive mapping, desktop restriction — each verified, not assumed to work
Build▼
What a GPO actually does

A GPO applies settings automatically to every user or computer in the OU (or domain) it's linked to. This week, build and test 3 real GPOs so the concept has something concrete to attach to — not just theory you can recite.

1
Password policy GPO: Group Policy Management → create a GPO linked at the domain level → Computer Configuration → Policies → Windows Settings → Security Settings → Account Policies. Enforce minimum length (12+), complexity, and account lockout threshold (5 attempts).
2
Drive mapping GPO: a new GPO linked to the Sales OU only, using Group Policy Preferences → Drive Maps, mapping a network drive (e.g. \\SERVER\Sales) automatically for anyone in that OU.
3
Desktop restriction GPO: linked to the Sales OU, under User Configuration → Administrative Templates → Control Panel, preventing access to Control Panel — a common real-world helpdesk-reducing policy.
Verify every GPO actually applies — never trust the GUI alone
on the domain-joined client, force a policy refresh and check what actually applied
gpupdate /force gpresult /r # summary — which GPOs applied, which didn't, and why gpresult /h report.html # full HTML report — open it, read it, don't skim
COMMON MISTAKE Building a GPO, linking it, and assuming it works because the GUI shows no errors. A GPO that "should" work but was never verified with gpresult is a common source of real production incidents — build the habit of always checking now, in the lab, before it costs you in a real job.
D42
File share permissions — NTFS vs. share, the layer most techs confuse
Two permission systems that combine, and the diagnostic pattern for "I see the folder but can't open it"
Build▼
Why this is a frequent point of confusion

A shared folder has two independent permission layers: share-level (set when you create the share) and NTFS-level (set on the folder itself, on disk). When both apply, the more restrictive one always wins — a share permission of "Everyone: Full Control" means nothing if the NTFS permission underneath denies access.

1
Create a folder, share it with "Everyone: Read/Write" at the share level.
2
Set the NTFS permission on the same folder to deny write access to your test user specifically.
3
Log in as that user, browse to the share (works — share permission allows it), try to create a file (fails — NTFS permission blocks it). This is exactly the "I can see the folder on the network but get access denied opening it" ticket you'll get in real support work.
4
Fix the NTFS permission to match intent, verify the write now succeeds.

D45
Samba file server — your Linux counterpart to the Windows share
Proper permission groups, setgid, group ownership — the Linux equivalent of NTFS permissions
Build▼
Building it, permission-conscious from the start
a Samba share with a real permission group, not wide-open access
sudo apt update && sudo apt install samba -y # Create a shared group and directory sudo groupadd itshare sudo mkdir -p /srv/samba/it sudo chown :itshare /srv/samba/it sudo chmod 2770 /srv/samba/it # setgid bit — new files inherit the group automatically # Add the share definition to /etc/samba/smb.conf: [it] path = /srv/samba/it valid users = @itshare read only = no sudo systemctl restart smbd sudo systemctl status smbd
ANALOGY — THE SETGID BIT Without setgid, every new file created in a shared folder inherits the creating user's personal group — meaning a second person on the team suddenly can't touch a file their teammate created five minutes earlier. Setgid forces every new file to inherit the folder's group instead, so the whole team keeps access automatically. It's the same intent as the Windows NTFS group-based permissions you set up in Week 6, just a different mechanism.
D46
SSH hardening — key-based auth, password login disabled
The single most common real-world security hardening step on any Linux server
Build▼
Why key-based auth matters

Password-based SSH is vulnerable to brute-force attacks in a way key-based auth simply isn't — an attacker can't guess a 256-bit private key. This is also a near-universal requirement in real production environments.

generate a key pair, install it, disable password login
# On your Ubuntu host (not the server VM) ssh-keygen -t ed25519 -C "lab-key" ssh-copy-id testuser@ # SSH in with the key, confirm it works passwordless, then harden sshd_config on the server sudo nano /etc/ssh/sshd_config # set: PasswordAuthentication no # set: PermitRootLogin no sudo systemctl restart sshd
COMMON MISTAKE Disabling password authentication before confirming key-based login actually works. Always test the key login successfully in a separate terminal session before restarting sshd with password auth disabled — locking yourself out of a VM is recoverable (via the VirtualBox console), but locking yourself out of a real remote server is a much worse day.

Log analysis — reading logs to answer real questions

Build▼
The questions real log analysis answers
practical log queries — practice each against your own server's real logs
# Who successfully logged in via SSH, and from where? grep "Accepted" /var/log/auth.log # Failed login attempts — a real security-relevant question grep "Failed password" /var/log/auth.log | tail -20 # What did a specific service log around the time it failed? sudo journalctl -u smbd --since "1 hour ago" # Search syslog for anything mentioning a specific error keyword grep -i "error" /var/log/syslog | tail -30

Generate a real failed-login event by deliberately mistyping a password via SSH from another terminal, then find the exact log line documenting it. This closes the loop between "I know the grep syntax" and "I can actually investigate an incident."

Configuring and testing — not just enabling
allow only what's needed, deny everything else by default
sudo ufw default deny incoming sudo ufw default allow outgoing sudo ufw allow 22/tcp # SSH sudo ufw allow 139,445/tcp # Samba sudo ufw enable sudo ufw status verbose

D52–53
Bulk user provisioning — the script that actually separates the tiers
A CSV, a PowerShell script, error handling, and a log — not 20 manual clicks
Capstone piece▼
Why this is the clearest automation signal in a junior sysadmin interview

Creating one AD user by hand is a helpdesk task. Creating 20 from a CSV, correctly placed into their OUs with the right group memberships, with errors caught and logged instead of silently failing, is a sysadmin task. Build this properly — with a try/catch block, not a script that only works when every input is perfect.

new_users.csv — your source data
FirstName,LastName,Department,OU Amaka,Johnson,Sales,Sales Chidi,Okafor,IT,IT Ngozi,Eze,Management,Management ... 17 more rows, realistic names, spread across your 3 OUs
bulk-create-users.ps1 — reads the CSV, creates every user, logs the result
$users = Import-Csv -Path "C:\scripts\new_users.csv" $logPath = "C:\scripts\provisioning_log.txt" foreach ($u in $users) { $sam = ($u.FirstName.Substring(0,1) + $u.LastName).ToLower() $upn = "$sam@corp.lab" try { New-ADUser -Name "$($u.FirstName) $($u.LastName)" \ -SamAccountName $sam -UserPrincipalName $upn \ -Path "OU=$($u.OU),DC=corp,DC=lab" \ -AccountPassword (ConvertTo-SecureString "Temp@2026!" -AsPlainText -Force) \ -Enabled $true -ChangePasswordAtLogon $true "$(Get-Date) - SUCCESS: $sam" | Out-File -Append $logPath } catch { "$(Get-Date) - FAILED: $sam - $_" | Out-File -Append $logPath } } # Verify: count how many were actually created vs. how many were in the CSV (Get-ADUser -Filter *).Count
COMMON MISTAKE Testing the script only with perfect data. Deliberately add one malformed row to your CSV (a missing OU, a duplicate SamAccountName) and confirm the script logs the failure clearly and keeps processing the rest — a script that silently dies on one bad row isn't automation you can trust.
D54
Virtualization discipline — checkpoint before risky change
Snapshot the domain controller, make a risky GPO change, deliberately roll back
Build▼
Practicing the full cycle

Snapshot the domain controller before a risky change (like a GPO that could lock out all users), make the change, verify it, and — deliberately, once — roll back a snapshot to prove you can recover cleanly. This exact discipline (checkpoint before risky change) is what separates a sysadmin who causes outages from one who doesn't.

1
Snapshot the DC, named clearly: before-lockout-policy-change.
2
Modify the password lockout policy to something deliberately too aggressive (e.g. lockout after 1 failed attempt).
3
Confirm the problem: a legitimate typo now locks out a test account immediately.
4
Restore the snapshot, verify the policy is back to sane defaults, and the test account is no longer locked.
D55
Real backup strategy — AD system state + Linux config
Beyond snapshots: what a real backup of a domain controller and a Linux server actually looks like

System state backup — the AD-specific backup that matters

A VM snapshot backs up everything; a system state backup is Windows Server's targeted backup of AD DS, SYSVOL, the registry, and boot files — the minimum needed to recover a domain controller without relying on the whole VM.

Windows Server Backup — system state, PowerShell
# Install the feature first if not already present Install-WindowsFeature Windows-Server-Backup # Run a one-time system state backup to a target location wbadmin start systemstatebackup -backupTarget:D: -quiet
Linux config backup — extending your Phase 1 script

Extend backup_home.sh logic to also archive /etc/samba/smb.conf and your crontab export — the configuration that would take real time to rebuild from memory if the server were lost.
