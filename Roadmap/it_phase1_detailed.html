a real diagnostic sequence, not a command list — practice this exact flow
# Scenario: "a service isn't responding" — walk this chain for real, on your own Ubuntu systemctl status ssh # is it even running? sudo journalctl -u ssh --since "10 min ago" # what does the log say happened recently? ss -tulpn | grep :22 # is anything actually listening on the port? ps aux | grep sshd # is the process itself alive? sudo systemctl restart ssh # restart, then re-check status

The ticket format — use this exact structure, every time, starting now

Whether you're using osTicket or Markdown files, every ticket follows the same 7-step structure. This format matters more than the tool it lives in.

ticket-template.md — copy this for every single ticket from here on
## Problem reported [Written from the user's point of view, in their language — not technical] ## Initial observations [What you saw when you first looked — error messages, symptoms, what's NOT wrong] ## Possible causes considered [List 2-3 theories, ranked by likelihood — this is the section most people skip] ## Tests performed [The exact commands/steps you ran to test each theory, and what each one showed] ## Root cause [What was actually wrong, confirmed — not assumed] ## Fix applied [The exact resolution steps] ## Verification [How you confirmed it's actually fixed, not just "looks fixed"] ## Prevention / lesson learned [What would stop this from happening again, or what you'd check first next time]

A ticket that shows a wrong theory ruled out before landing on the right one is more convincing to a hiring manager than one that jumps straight to the answer — it's proof of actual diagnostic thinking, not a lucky guess.

Must-know concepts before touching a single lab
IP addressing, public vs private, gateway, DNS, DHCP, MAC, ports, TCP vs UDP, NAT, firewall basics
Foundation▼
The vocabulary — understood, not memorized
ConceptWhat it actually means
Private vs public IPPrivate (10.x, 172.16–31.x, 192.168.x) only routes inside your local network; a router's NAT translates it to one public IP for the internet.
Default gatewayThe device (usually your router) that traffic goes through to leave your local network.
DNSTranslates human-readable names (google.com) into IP addresses computers actually route by.
DHCPAutomatically assigns an IP, gateway, and DNS server to a device when it joins a network — the alternative is manually configuring every device by hand.
MAC addressA hardware-burned identifier for a network interface, used at the local-network (Layer 2) level, distinct from the IP address used for routing.
TCP vs UDPTCP confirms delivery (web browsing, email — accuracy matters); UDP doesn't (video calls, streaming — speed matters more than a dropped packet).
NATNetwork Address Translation — how one public IP represents many private devices to the outside internet.
FirewallRules that allow or block traffic based on port, protocol, or source — your first line of network-level security.

Spend the rest of today on your real Ubuntu host: run ip a and identify your own IP, gateway, and DNS server. Run ip route and explain, in your own words, what each line means.

The diagnostic sequence — drilled until it's habit, not a lookup
ipconfig/ip a → ping gateway → ping 8.8.8.8 → nslookup → tracert — memorized by doing it, repeatedly
Build▼
The sequence real technicians use, and why the order matters
CommandWhat it tells you
ipconfig /all (Win) · ip a (Linux)Does this machine even have a valid IP, gateway, and DNS server?
ping [gateway]Can this machine reach the local network at all?
ping 8.8.8.8Can this machine reach the internet by IP — rules out DNS as the problem.

D11
Subnetting — brute-force practice, 20–30 min daily from here on
CIDR notation, usable host ranges, the one topic that punishes cramming
Practice▼
Why this deserves its own daily habit, not a single study day

Subnetting is the single most memorization-resistant topic in networking — you either fluently convert CIDR notation to usable host ranges under time pressure, or you don't. This is exactly the kind of material that responds to spaced repetition, not cramming: 20–30 minutes daily, continuing well past this week, beats one long session every time.

the core calculation, worked through
# Given: 192.168.1.0/26 # /26 = 26 network bits, 6 host bits remaining (32-26=6) # Total addresses = 2^6 = 64 # Usable hosts = 64 - 2 (network + broadcast) = 62 # Subnet size = 256 - 192 (the /26 block size in the last relevant octet) = 64 # So: Network = 192.168.1.0, Broadcast = 192.168.1.63 # Usable range = 192.168.1.1 - 192.168.1.62 # Next subnet starts at 192.168.1.64

Use subnettingpractice.com daily — 15 minutes, timed, every day this week and into Week 3. By Week 4 you should solve a /27 or /28 problem in under 60 seconds without hesitation.

ANALOGY — THE PIPELINE A PowerShell pipeline (|) passes structured objects from one cmdlet to the next, not plain text like Bash does. That's why Get-Process | Sort-Object CPU just works — you're sorting real process objects by a real property, not parsing text output. Understanding this difference is what separates someone who copies PowerShell one-liners from someone who can actually reason about why one works and another doesn't.

Build▼
The permission model, understood conceptually

Every file has an owner, a group, and a permission set for "other" (everyone else) — each with read/write/execute independently. chmod 750 means owner gets read+write+execute (7), group gets read+execute (5), other gets nothing (0). Understanding the math behind the numbers, not just memorizing common combinations, is what lets you reason about an unfamiliar permission set under pressure.

Day 18–19 lab: break and fix a permissions problem, command line only
# Create a file only root can read, then try to access it as testuser sudo useradd -m testuser sudo -u testuser touch /home/testuser/secret.txt sudo chmod 600 /home/testuser/secret.txt sudo chown root:root /home/testuser/secret.txt # Now, as testuser, confirm the failure and diagnose why su - testuser cat /home/testuser/secret.txt # Permission denied — explain exactly why in your ticket # Fix: restore correct ownership exit sudo chown testuser:testuser /home/testuser/secret.txt
COMMON MISTAKE Running every command as root/Administrator "to make it easier." Real environments enforce least privilege, and interviewers ask about it directly. Diagnose and fix permission problems as the affected user first, escalating only when the fix genuinely requires it — and explain in your ticket notes why escalation was necessary.
Bash scripting basics — beyond just running commands

Linux commands and Bash scripting are two different skills — knowing chmod doesn't mean you can write a script that uses it conditionally. This is the foundation Month 2's automation work depends on: variables, arguments, conditionals, loops, exit codes, functions.

a real small script combining variables, a conditional, and an exit code
#!/bin/bash # check_user.sh — verifies a user exists, exits with a meaningful code USERNAME=$1 if [ -z "$USERNAME" ]; then echo "Usage: ./check_user.sh <username>" exit 1 fi if id "$USERNAME" &>/dev/null; then echo "$USERNAME exists" exit 0 else echo "$USERNAME does not exist" exit 2 fi

Build▼
Snapshot vs. backup — a distinction worth being precise about

A snapshot captures the entire VM state at a point in time and lives alongside the VM — fast to create and restore, but not a substitute for an actual backup, since a snapshot chain can grow large and a corrupted VM disk can take the snapshot down with it. A backup is an independent copy of specific data, stored separately, meant to survive the original failing entirely. Both matter, for different reasons.

1
On your Ubuntu Server VM, deliberately delete a file you care about — then restore it from a manual backup (a simple tar archive you created beforehand), not from a snapshot.
2
Practice a full VM snapshot restore: take a snapshot, make an intentionally destructive change (like removing a critical package), then restore the snapshot and verify the VM is back to its prior state.
3
Write a short SOP: "when to use a snapshot vs. when to use a real backup" — this is genuinely strong interview material most junior candidates can't speak to clearly.
a simple backup script — the foundation for Month 2's automated version
#!/bin/bash # backup_home.sh — archives a user's home directory with a timestamp BACKUP_DIR="/backups" TIMESTAMP=$(date +%Y%m%d_%H%M%S) mkdir -p $BACKUP_DIR tar -czf "$BACKUP_DIR/testuser_$TIMESTAMP.tar.gz" /home/testuser echo "Backup created: testuser_$TIMESTAMP.tar.gz"

Security fundamentals every support tech needs

Foundation▼
The core vocabulary
Malware typeHow it typically presents to a user
VirusAttaches to legitimate files/programs, spreads when the host file is run or shared
WormSelf-replicates across a network without needing a host file or user action
TrojanDisguised as legitimate software; the user installs it willingly, not knowing what it actually does

MFA and phishing — the two topics with the most real-world weight

Multi-factor authentication types: SMS (weakest — vulnerable to SIM-swap attacks), authenticator app (TOTP — stronger), hardware key (strongest — phishing-resistant). Phishing red flags to be able to name specifically: mismatched sender domain (hover, don't trust the display name), urgency/fear language ("your account will be suspended"), suspicious links (hover to preview the actual URL before clicking), and requests for credentials or payment that bypass normal channels.

Security thinking isn't a separate skill bolted on this week — it's asking "what access does this actually need, and what access does it not need?" every single time, on every system, from now on.
D24
The 6-step troubleshooting methodology — memorized cold
CompTIA's official sequence — appears on the exam, and is exactly what interviewers want to hear
Foundation▼
The exact 6 steps
1
Identify the problem — gather information, question the user, identify recent changes.
2
Establish a theory of probable cause — start with the obvious, question the obvious if it's wrong.
3
Test the theory to determine the cause — confirm before you act.
4
Establish a plan of action and implement the solution.
5
Verify full system functionality and implement preventive measures.
6
Document findings, actions, and outcomes.

Notice this maps almost exactly onto the 7-step ticket format you've been using since Week 1 — that's not a coincidence, it's the same discipline. From today, explicitly reference these 6 steps in every remaining ticket, and practice reciting them without notes until it's automatic.

If you've been logging tickets since Week 1, you should already have 6+ real ones sitting in your queue. This isn't about inventing 10 from scratch — it's about selecting your 10 strongest, polishing them to the full 7-step standard, and filling any category gaps with 1–2 new realistic scenarios.

Fill any gaps with these realistic scenarios if needed
1
Hardware: "laptop won't boot" (diagnose via POST beep codes or BIOS access, isolate to RAM/storage/power) and "printer not responding" (spooler service check, driver reinstall).
2
Security: "user reports a suspicious email" (walk through your phishing red-flag checklist) and "user locked out after failed MFA attempts" (verify identity through a secondary channel, reset correctly).
COMMON MISTAKE Writing tickets that are too easy or too vague ("computer broken, fixed it"). A hiring manager reading these should see real diagnostic thinking — the wrong theory you ruled out, not just the right answer you landed on.
Write 2 full SOPs from your strongest, most instructive tickets

Pick the 2 tickets that taught you the most, and expand them into standalone SOPs — documents detailed enough that a stranger could follow them cold, without asking a question. Good candidates: the DNS troubleshooting sequence, or the Windows account lockout recovery process.
