Why AWS deep and Azure broad, not both equally
You have one month, not two. Splitting it evenly between AWS and Azure would leave you shallow in both — good enough to recognize service names, not good enough to actually diagnose a problem in either. Going deep on one cloud and broad on the second means you can build real things in AWS, and speak credibly about Azure in an interview without pretending to expertise you don't have.

D61
Account setup, billing alarm, root vs. IAM user — in that order
The single habit that prevents every "surprise bill" story from junior cloud learners
Foundation▼
Before touching a single service

Create an AWS Free Tier account. Before anything else, set a billing alarm at a low threshold — this single habit prevents the most common beginner mistake: an accidentally-running resource generating a surprise bill. Then create an IAM user for yourself with administrator access for daily work, instead of using the root account — root is for account-level tasks only, from day one, no exceptions.

create your daily-use IAM user and a billing alarm — AWS CLI
# After installing and configuring the AWS CLI with root credentials once: aws iam create-user --user-name daily-admin aws iam attach-user-policy --user-name daily-admin \ --policy-arn arn:aws:iam::aws:policy/AdministratorAccess aws iam create-access-key --user-name daily-admin # Switch to using these credentials for everything from here on — # never use root access keys for daily work
COMMON MISTAKE Assuming "Free Tier eligible" means "cannot be charged, ever." Some resources have free-tier limits by hours-per-month or storage-per-month — exceed them and billing starts silently. Check each service's specific free-tier terms before creating it, not after.
D62–63
IAM deep dive — users, groups, policies, least privilege in practice
The exact same conceptual model as Active Directory, cloud-native
Build▼
Why this feels familiar

IAM controls who can do what in an AWS account — users, groups, and policies map almost directly onto the AD users, security groups, and GPOs you built in Phase 2. The mechanism is different; the thinking is the same: grant permissions to a group, not an individual, and grant only what's actually needed.

create a least-privilege group and verify it actually restricts access
# Create a group with read-only access to EC2 and S3 aws iam create-group --group-name SupportTeam aws iam attach-group-policy --group-name SupportTeam \ --policy-arn arn:aws:iam::aws:policy/ReadOnlyAccess # Create a user, add to the group aws iam create-user --user-name support-tech1 aws iam add-user-to-group --user-name support-tech1 --group-name SupportTeam aws iam create-access-key --user-name support-tech1 # Switch to support-tech1's credentials, then TRY a write action — it must fail aws ec2 terminate-instances --instance-ids i-0123456789abcdef0 # Expected: AccessDenied — this failure is your proof the policy actually works
ANALOGY — VERIFY, DON'T ASSUME A permission policy that looks correct on paper is a theory, not a fact. Just like testing a GPO with gpresult in Phase 2, the only real proof an IAM policy works is watching a denied action fail exactly where you expect it to. A policy you haven't tested against a should-fail case is a policy you don't actually understand.

EC2 — launch, connect, and understand security groups

Build▼
Launching and connecting
1
Launch a t2.micro EC2 instance (free tier eligible) running Amazon Linux, in the default VPC to start.
2
Generate or reuse a key pair, and SSH into the instance from your Ubuntu host — the same key-based auth pattern from Phase 2's Samba server.

launch and connect via AWS CLI
aws ec2 run-instances --image-id ami-0abcdef1234567890 \ --instance-type t2.micro --key-name my-key \ --security-group-ids sg-0123456789abcdef0 # Once running, grab its public IP and connect aws ec2 describe-instances --instance-ids i-0123456789abcdef0 \ --query 'Reservations[0].Instances[0].PublicIpAddress' ssh -i my-key.pem ec2-user@<public-ip>
COMMON MISTAKE Leaving free-tier resources running after the lab session ends. Stop or terminate every EC2 instance at the end of each study session — set this as a personal, non-negotiable rule.
D66
AWS CLI fluency — scripting the console, not clicking through it
The commands you'll use daily, chained together like the diagnostic sequences from earlier phases
Build▼
A real script — start/stop automation, the AWS equivalent of your cron habit
a Bash script that stops every running EC2 instance — your personal cost guardrail
#!/bin/bash # stop_all_ec2.sh — run this at the end of every AWS study session INSTANCE_IDS=$(aws ec2 describe-instances \ --filters "Name=instance-state-name,Values=running" \ --query 'Reservations[*].Instances[*].InstanceId' --output text) if [ -z "$INSTANCE_IDS" ]; then echo "No running instances found." else aws ec2 stop-instances --instance-ids $INSTANCE_IDS echo "Stopped: $INSTANCE_IDS" fi

Commit this script to your GitHub repo today, and actually run it at the end of every session from here on — it's a small habit that directly protects your budget for the rest of the month.

D68
S3 — buckets, policies, and the accidental-exposure scenario
A deliberately misconfigured public bucket, caught and fixed — a real, frequently-tested support scenario
Build▼
Buckets, uploads, and policy misconfiguration
1
Create an S3 bucket, upload a test file via console or CLI.
2
Deliberately misconfigure the bucket policy to allow public read access — observe AWS's warning banner in the console (it actively tries to stop you from doing this by accident, for good reason).
3
Confirm the exposure: try accessing the object's URL from a private/incognito browser window, unauthenticated.
4
Correct it: re-enable "Block all public access" at the bucket level, verify the object is no longer reachable.
the bucket policy that caused the exposure — study it, then remove it
{ "Version": "2012-10-17", "Statement": [{ "Effect": "Allow", "Principal": "*", "Action": "s3:GetObject", "Resource": "arn:aws:s3:::your-bucket-name/*" }] }
COMMON MISTAKE Not understanding that "Principal": "*" means literally anyone on the internet, unauthenticated. This single line is behind a large share of real-world cloud data breaches — recognizing it on sight is a genuinely valuable interview and on-the-job skill.
D69
Custom VPC — the networking foundation every "can't reach the internet" ticket depends on
Public and private subnets, an internet gateway, route tables
Build▼
Building it from scratch, understanding each piece
ComponentWhat it actually does
VPCYour isolated slice of AWS network — everything else lives inside it
Public subnetHas a route to the internet gateway — resources here can be reached from (and reach) the internet
Private subnetNo direct internet route — resources here are isolated, reached only from inside the VPC
Internet GatewayThe door between your VPC and the public internet
Route tableThe rules determining where traffic from a subnet is allowed to go
1
Create a custom VPC (e.g. 10.0.0.0/16), then a public subnet (10.0.1.0/24) and a private subnet (10.0.2.0/24).
2
Create and attach an Internet Gateway to the VPC.
3
Create a route table for the public subnet with a route to the Internet Gateway (0.0.0.0/0), and associate it with the public subnet only.
4
Launch an EC2 instance in the public subnet, confirm it can reach the internet. Launch one in the private subnet, confirm it can't — this is the exact "why can't this resource reach the internet" scenario you'll diagnose in real tickets.
D70
Security Groups deep dive — diagnosing blocked legitimate traffic
Stateful rules, the difference from NACLs, and a real diagnosis exercise
Build▼
Security Groups vs. Network ACLs

Security Groups are stateful (allow the response to an allowed request automatically) and attach to instances; Network ACLs are stateless (you must explicitly allow both directions) and attach to subnets. Most day-to-day troubleshooting involves Security Groups — NACLs are usually left at their permissive defaults unless there's a specific reason to lock down at the subnet level.

Day 70 lab: deliberately misconfigure a security group, then diagnose it blind
# Remove the inbound rule allowing HTTP (port 80) from a web server's security group aws ec2 revoke-security-group-ingress --group-id sg-0123456789abcdef0 \ --protocol tcp --port 80 --cidr 0.0.0.0/0 # Now diagnose as if a real ticket arrived: "users can't reach our web server" # Confirm the instance itself is running and the web service is up (SSH in, check the service) # Confirm DNS/IP is correct # Check the security group's inbound rules — this is where you'll find the gap aws ec2 describe-security-groups --group-ids sg-0123456789abcdef0 # Fix: re-add the rule aws ec2 authorize-security-group-ingress --group-id sg-0123456789abcdef0 \ --protocol tcp --port 80 --cidr 0.0.0.0/0
D71
CloudWatch — monitoring that's actually verified to work
A CPU alarm, tested with a real stress event, not just configured and trusted
Build▼
Set it up, then break it on purpose to prove it works
1
Create a CloudWatch alarm on your EC2 instance that triggers if CPU usage exceeds 80% for 5 minutes.
2
SSH into the instance and generate a real CPU spike: yes > /dev/null & run a few times, or use stress if installed.
3
Watch the alarm actually transition to ALARM state in the console — this is the same discipline as verifying a GPO with gpresult or a security group with a should-fail test.
COMMON MISTAKE Configuring an alarm and trusting it works without ever triggering it. An alarm nobody has verified actually fires is worse than no alarm at all — it creates false confidence.

D82
The shared responsibility model — the concept every cloud security question tests
Where AWS/Azure's responsibility ends and yours begins, with concrete examples on each side
Foundation▼
The line, drawn precisely

AWS and Azure secure the underlying infrastructure — physical data centers, the hypervisor, network hardware. You are responsible for everything above that: data encryption, access management, security group/firewall rules, and OS-level patching on any VM you run. Almost every real-world cloud security incident traces back to someone misunderstanding where that line sits — usually an overly permissive security group or a public S3 bucket, exactly like the Week 10 exercise.

1
Write down one concrete example from your own labs on the provider's side: AWS ensuring the physical data center hosting your EC2 instance is secure.
2
Write down one concrete example on your side: the Week 10 public S3 bucket misconfiguration — entirely your responsibility to prevent, not AWS's.

Be able to explain this model clearly, with your own examples, without hesitation — it's one of the most frequently asked concept questions in cloud support interviews.

Practice exams — 2 full-length, review every miss

Practice▼
How to actually use a practice exam

Take the first full-length practice exam under real time pressure — no pausing, no notes. Afterward, don't just check the score: for every question you got wrong, go back to the concept and connect it to a lab you did this month if possible, or a specific doc page if not. Take the second practice exam 1–2 days later, after reviewing weak areas — the improvement between the two tells you honestly whether you're ready.

COMMON MISTAKE Memorizing practice exam answers instead of understanding why each one is correct. Real exam questions are scenario-based and reworded — memorized answers to specific practice questions won't transfer to the actual exam's phrasing.
